# Q01 上下文 · 需求与边界

> 来源：`course/固定材料/业务原话练习.md`（Q01 业务原话）、`course/固定材料/业务原话与FAQ.md`（工单台需求说明）、`course/契约/接口与数据.md`（v1 契约）。

## 一、业务原话与我的理解

> 业务原话：「我们需要个工单台，大家报上来的问题有人接，负责人一眼能知道进度。手机上也得能用。」

「大家」：指的是上报人 `user`，对应字段 `ownerId`，负责填写标题、描述、分类并提交工单；

「有人接」：指的是工单被指派给处理人 `staff`，对应字段 `assigneeId`，状态由 `open`（待处理）推进到 `in_progress`（处理中）；

「负责人」：指的是可总览全部未归档工单的管理人员 `manager`，负责分派与状态推进；

「进度」：对应工单当前的 `status`，取值只有 `open`／`in_progress`／`resolved` 三种。

**原话中的含糊之处**：① 原话里的「接」是主动认领还是被动分派不清楚，接口只提供 manager 分派 `assigneeId`，没有 staff 认领入口；② 没说清楚 user 能否撤回自己的单；③ 「进度」只落到三态，能否表达业务想看的进度待确认。



## 二、目标

建立一个统一的工单工作台：用户提交问题，工作人员跟进，管理者分配并查看进度；桌面和手机都可操作；既有 v1 接口继续提供原行为。

## 四、角色与操作对照表

按角色逐项记录「可操作对象／前置状态／成功结果／禁止情形」。核心依据是 `course/契约/接口与数据.md` 中 v1 的 PATCH 角色表。

| 角色 | 可见范围（均未归档） | 可改字段 | 状态规则 | 异常情形 |
|---|---|---|---|---|
| `user` | 本人 `ownerId` 的工单（三种状态都能看） | 仅 `title`、`description`、`category` | 仅 `open` 允许编辑；`in_progress`／`resolved` 拒绝编辑 | 改 `status`／`assigneeId` → 403 `ACTION_FORBIDDEN`；非 `open` 状态编辑 → 409 `INVALID_STATE`；旧版本 → 409 `VERSION_CONFLICT`；无业务字段 → 400 `EMPTY_CHANGE`；含未知字段 → 400 `UNKNOWN_FIELD`；访问他人单 → 404 `TICKET_NOT_FOUND` |
| `staff` | `assigneeId` 为本人 的工单 | 仅 `status` | `open → in_progress` 或 `resolved`；`in_progress → resolved`；`resolved` 不能再流转，也不能设回 `open` | 改 `title`／`description`／`category`／`assigneeId` → 403 `ACTION_FORBIDDEN`；非法流转（如 `resolved → open`）→ 409 `INVALID_STATE`；旧版本 → 409 `VERSION_CONFLICT`；非本人处理的单 → 404 `TICKET_NOT_FOUND` |
| `manager` | 全部未归档工单 | `status`、`assigneeId` | 三种状态均可设置，因此可以 `resolved → open`（重开）；`assigneeId` 可设为 staff 或 `null`（不分配） | 改 `title`／`description`／`category` → 403 `ACTION_FORBIDDEN`；`assigneeId` 不是 staff → 400 `INVALID_ASSIGNEE`；旧版本 → 409 `VERSION_CONFLICT`；归档后访问 → 404 |

**本表之外的两个动作**（不在 PATCH 范围内，单列）：

| 动作 | 谁能做 | 约束与异常 |
|---|---|---|
| 新建工单 `POST /v1/tickets` | 仅 `user` | JSON 只允许 `title`／`description`／`category`；含未知字段 → 400 `UNKNOWN_FIELD`；staff／manager 调用 → 403 `ACTION_FORBIDDEN`；新建后固定为 `open`／`normal`／未分配／`version` 1 |
| 归档 `DELETE /v1/tickets/:id` | 仅 `manager` | 必须带 `version`；非正整数 → 400 `INVALID_VERSION`；旧版本 → 409 `VERSION_CONFLICT`；其他角色 → 403 `ACTION_FORBIDDEN`；归档后所有角色访问详情与事件均为 404，且没有恢复接口 |

> 说明：材料中**没有**「附件」「处理备注」「进度记录」「关闭」这些字段或状态。`status` 只有三个值；「关闭」在本系统中对应的动作是 `resolved`（已解决）或 `archived`（归档），两者含义不同。

## 五、五个待确认问题

五条都按「问题／出处·核对结果／影响」三段写。凡材料已有依据的，标为「已确认」，只把真正缺的部分列为待确认。

### 问题 1：用户能否撤回自己提交的工单？

**出处 / 核对结果**：**部分已确认**。`course/契约/接口与数据.md` 的 v1 PATCH 角色表规定 `user` 只能改 `title`／`description`／`category`，且「仅 `open` 允许编辑」；`DELETE` 接口「仅 `manager`」。也就是说，**用户目前没有任何撤回自己工单的路径**，只能请管理者代为归档。业务上是否需要给用户开撤回入口，材料未写 —— 待确认。

**影响**：两条路线。① 沿用现状：用户详情页只放「编辑」（仅 `open` 可用），撤回走 manager 归档，接口不变。② 给用户撤回能力：需修改 `DELETE` 的权限边界，从「仅 manager」扩到「`ownerId` 本人」，属于**接口契约变更**，同时要确定是否限制「只能撤回 `open` 状态的单」。两条路线对前端按钮、接口权限、测试用例的要求完全不同。

### 问题 2：「有人接」是 staff 主动认领，还是 manager 派单？

**出处 / 核对结果**：**实现已确认，业务意图待确认**。`接口与数据.md` 的 PATCH 角色表中，`assigneeId` 只有 `manager` 能改，`staff` 的可改字段只有 `status` —— 系统**不提供 staff 主动认领的入口**。而业务原话说的是问题「有人接」，读起来更像自己接。业务能否接受"只能被动派单"这种设计，材料未写 —— 待确认。

**影响**：决定工单列表是否出现「接单」按钮、是否需要新增「认领」接口，以及 staff 第一次能看到某张单的时机（现在必须等 manager 派给自己）。若确定为被动派单，前端只需显示「等待分派」，不必做认领交互。

### 问题 3：「进度」只用三种状态是否足够？

**出处 / 核对结果**：**状态取值已确认**（`open`／`in_progress`／`resolved`，见字段表）；但「三态能否表达业务想看的进度」材料未写。原话说「负责人**一眼能知道进度**」，而现有模型没有进度百分比、没有计划完成时间，事件虽然记录了 `CREATED`／`UPDATED`／`ARCHIVED`，却没有在列表或详情里展示成时间线。这一点待确认。

**影响**：影响列表与详情的进度呈现方式；是否需要新增字段（例如预计完成时间、当前处理环节）；是否需要把 `UPDATED` 事件按时间排成「处理轨迹」；也影响 Q04 卡片上只显示一个状态标签是否够用。

### 问题 4：工单归档后所有角色都读不到，历史追溯怎么办？

**出处 / 核对结果**：**归档行为已确认**（`archived` 后详情与事件 HTTP 均 404；记录与事件仍保留在库中；没有恢复接口；manager 的可见范围同样只到「未归档」）。「归档后是否需要可查」材料未写 —— 待确认。

**影响**：决定是否需要新增「归档列表／只读历史」视图与对应接口、是否需要记录归档原因与归档人、以及数据保留策略。Q07 迁移 SQLite 时也要一并决定归档行对哪些角色可见。

### 问题 5：手机端的「也能用」覆盖哪些动作？

**出处 / 核对结果**：**部分已确认**。`业务原话与FAQ` 写「桌面和手机均可操作」，`规范/UI与交互` 写「手机可由表格变卡片，保持字段与行为一致」，所以「字段与行为一致」已有依据；但「是否所有角色、所有动作都要在手机上完成」材料未写 —— 待确认。

**影响**：决定移动端页面范围与导航结构。**本次倾向**：手机端只保留查看、提交、改状态这类低风险的日常动作；批量操作与归档只在桌面端提供，避免在窄屏误触。若确认需要全量支持，则要为高风险操作补二次确认，并重新权衡 320／390 宽度下的操作密度。

## 七、接口、权限、数据与界面约束

- **接口**：v1 全部路径与行为必须保持兼容；错误统一 `{error:{code,message,fields?},requestId}`；状态码 400／401／403／404／409／413／415／500 各司其职。
- **权限**：角色来自固定 `actors` 表；可见性先于查询与分页生效；不可见与不存在统一 404。
- **数据**：`version` 每次有效写入递增，旧版本必须拒绝而不覆盖；归档后保留记录与事件，但 HTTP 一律 404。
- **界面**：沿用共用控件与设计变量（`course/design-tokens.json`）；检验 320／390／768／1440 CSS 像素，至少提供 390 与 1440 截图；触摸目标 44×44；正文对比度 4.5:1。
