# Q01 上下文：工单台需求梳理

## 一、业务原话
> 我们需要个工单台，大家报上来的问题有人接，负责人一眼能知道进度。手机上也得能用。

## 二、需求理解
业务想要搭建一个平台：用户提交需求也就是工单。工作人员接收处理工单，负责人主要查看进度。页面支持pc和手机端查看。

## 三、五个待确认问题（答案不同会直接改变实现）

> 核对来源：业务原话与FAQ.md、契约/接口与数据.md

### 1. 原话里的「大家」，哪些角色可以提交工单？
- **核对结果**：✅ 已确认。只有 `user`（普通用户）可以新建工单；`staff`、`manager` 不能提交工单。
- **实现影响**：POST /v1/tickets 的权限校验只放行 user 角色，其他角色调用直接拦截；如果确认结果是全员可提交，后端权限判断和前端入口按钮都要改。
- **资料出处**：契约/接口与数据.md（新建工单接口权限约束）

### 2. 原话「有人接」，由哪个角色承接工单？承接后可以操作哪些字段？
- **核对结果**：✅ 已确认。由 `staff`（工作人员）承接工单；staff 只能修改分配给自己工单的 `status`，不能修改 `title`、`description`、`category`。
- **实现影响**：更新接口按角色放字段——staff 的 payload 只允许状态字段；如果允许 staff 改标题或分类，字段校验和前端表单都要放开。
- **资料出处**：契约/接口与数据.md（更新工单接口的角色与字段约束）

### 3. 原话「负责人」对应系统哪个角色？能看到哪些工单？
- **核对结果**：✅ 已确认。负责人对应 `manager`（管理者），可以查看全部工单；`staff` 只能看到分配给自己的工单；`user` 只能看到自己提交的工单。
- **实现影响**：列表接口按角色做数据范围过滤；如果负责人要按分组/部门筛选，接口和前端筛选条件都要额外加。
- **资料出处**：契约/接口与数据.md（角色可见范围说明）

### 4. 原话「进度」具体指哪些信息？前端要展示哪些工单字段作为进度？
- **核对结果**：❓ 待确认。业务原话、FAQ 和接口规范都没有规定进度面板的展示字段清单；基线默认展示 `status`（状态）、`assigneeId`（处理人）、`version`（版本）。
- **实现影响**：如果业务要求展示优先级、截止时间、更新时间等字段，前端列表和接口返回结构都要补。
- **资料出处**：业务原话与FAQ.md（无明确约定）；契约/接口与数据.md（工单存储字段定义）

### 5. 工单进度变更后，负责人是否能看到变更历史？
- **核对结果**：❓ 待确认。原话没有说明是否需要在页面上展示变更记录；基线阶段服务端会追加事件记录（CREATED / UPDATED），但前端不默认展示历史时间线。
- **实现影响**：如果要求展示历史，需要额外加事件查询接口和前端时间线组件；不展示则只保留后台事件记录。
- **资料出处**：业务原话与FAQ.md（无明确约定）；契约/接口与数据.md（事件记录说明）

## 四、需求分类

### ✅ 已确认需求
1. 角色分三类：`user` / `staff` / `manager`，接口按角色做权限和数据范围控制。
2. `user` 可以新建工单；工单初始状态为 `open`，`version = 1`。
3. `staff` 处理分配给自己的工单，只允许变更状态。
4. `manager` 可以查看全部工单、分配处理人、变更状态、归档工单。
5. 工单基础字段：`title`、`description`、`category`、`status`、`assigneeId`、`version`。
6. 页面需要响应式适配，手机浏览器可访问。
7. 基线使用 JSON 文件存储工单与事件数据。

### ❓ 待确认需求
1. 进度展示的详细字段清单（是否要优先级、截止时间、更新时间等）。
2. 变更历史是否需要在前端页面展示。
3. 移动端窄屏下哪些控件必须保留、哪些可以折叠，以及页面断点和字号细则。

### ❌ 本次排除的需求
1. 消息通知、推送、站内聊天功能。
2. 文件上传、图片附件。
3. 工单导出、报表统计。
4. 账号注册与正式登录体系（基线用请求头 `X-Training-Actor` 模拟角色身份）。

## 六、接口约束
1. **身份识别**：通过请求头 `X-Training-Actor` 传入模拟身份（user / staff / manager），基线不做正式鉴权。
2. **新建工单**：`POST /v1/tickets`，仅 user 可调用；请求体只允许 `title`、`description`、`category`，多余字段按非法处理。
3. **字段校验**：`title` 长度 1–60；`description` 允许为空、最长 1000；`category` 只能取 `support` / `billing` / `other`。
4. **更新工单**：`PATCH /v1/tickets/:id`，按角色放行不同字段；状态冲突、资源不存在、越权操作分别返回对应错误码。

## 七、页面验收条件
1. 本地启动工程后，Vue 入口页面可正常打开，控制台无报错。
2. 三类角色进入页面后，只能看到权限范围内的内容和操作入口。
3. 手机窄屏下核心表单、按钮、列表可读可用，不出现横向溢出。
4. 草稿清洗函数对空值、非字符串、超长、非法分类能正确收集错误。
5. 工单流转（提交 → 接手 → 状态变更）符合接口权限规则。

## 八、验证方法
1. 启动本地工程，浏览器访问 Vue 入口，分别在桌面和手机视口下检查布局。
2. 切换 user / staff / manager 三个模拟身份，分别测试新建、接手、查看工单，确认越权操作被拦截。
3. 构造空标题、超长描述、非法分类等输入，验证 `normalizeDraft` 的清洗与错误收集。
4. 跑基线测试，追踪一次新建工单请求，确认服务端接收请求、校验字段、写入工单与事件记录的完整链路。

## 九、角色 — 页面 — 操作 — 异常对照表

| 角色 | 可用页面 | 允许操作 | 异常情况 |
| ---- | -------- | -------- | -------- |
| user（普通用户） | 工单列表、新建表单、本人工单详情 | 创建工单；编辑自己名下 `open` 状态工单的草稿；查看本人工单 | 操作他人工单返回 403；编辑已归档工单返回 404；编辑非 `open` 工单返回 409 |
| staff（工作人员） | 分配给自己的工单列表、工单详情 | 接手工单；变更工单状态（open → in_progress / resolved） | 操作未分配给自己的工单返回 403；修改标题/分类被拦截；归档工单返回 404 |
| manager（管理者） | 全部工单列表、工单详情 | 查看全部工单；分配处理人；变更任意工单状态；归档工单 | 归档后所有角色访问该工单返回 404；传入非法处理人返回 400 |

## 十、页面尺寸与异常处理要求
- **页面尺寸**：响应式布局，兼容手机窄屏与桌面宽屏；核心操作按钮和表单控件在窄屏下保持可见、可点。
- **异常处理**：参数非法返回 400；权限不足返回 403；资源不存在返回 404；状态冲突返回 409；前端需要能展示接口返回的错误信息。
- **示例身份**：基线通过 `X-Training-Actor` 请求头模拟 user / staff / manager，不是真实登录账号，没有密码和会话。

## 十一、JSON 存储的局限
基线阶段工单数据写入本地 JSON 文件，存在以下局限，后续任务再切换到数据库：
1. 没有数据库层面的字段类型与约束，校验只能靠代码保证。
2. 并发写入容易互相覆盖，靠 `version` 字段做乐观并发控制。
3. 不支持索引，数据量增大后查询性能会下降。
4. 没有事务能力，写入中途异常可能出现工单与事件记录不一致。

## 十二、基线新建工单请求链路（审核问答备用）
1. **识别角色**：服务端读取请求头 `X-Training-Actor`，解析出当前模拟身份；不是登录鉴权，仅用于训练场景的角色模拟。
2. **校验字段**：先判断角色是否允许新建（仅 user）；再校验请求体只含 `title` / `description` / `category`，检查长度与分类白名单，非法则返回 400。
3. **写入数据**：生成工单 ID，默认 `status = open`、`version = 1`、`priority = normal`；写入工单存储；同时追加一条 `CREATED` 事件记录。

## 十三、日语说明（审核提问备用）
**質問**：この要件について、確認済みの点と未確定の点を説明してください。

**回答**：
確認済みの点は、ユーザーがチケットを作成できること、スタッフは担当チケットのステータスのみ変更できること、管理者は全チケットを閲覧・管理できること、画面はスマホ対応のレスポンシブレイアウトが必要なことです。
未確定の点は、進捗として表示する項目の詳細、変更履歴を画面に表示するかどうか、モバイル画面の細かいレイアウトルールの3点です。
